# ADR 0001: 根拠付きシナリオ算出器として作り、入力は手入力の YAML に限る（自動収集しない）

## 背景

spec は、店舗 URL を入れると Web 上の情報から収益構造を推定するシステムを目的にしている。一方で spec 自身が、実績データで誤差を測るまでは「予測モデル」を名乗らないこと、外部ソースは利用条件を先に確認することを求めている（spec 4 章・16 章）。

再検証（docs/research/2026-10-30-spec-verification.md）で次を確認した。

- ホットペッパー Webサービスの利用ガイドは「飲食店から金銭等の対価を得るビジネスに関わるサイトでの利用」と「店舗等の情報そのものの再販」を禁止している（FND-10）
- Google Places API はキャッシュ・保存に制限があり、混雑状況・来客数の項目は無い（FND-10）
- 求人サイト（グルメキャリー）は WebFetch・ブラウザとも 403 だった（FND-8）
- 食べログ・トレタに一般向けの公開 API は無い

## 決定

- MVP は**根拠付きシナリオ算出器**として作る。出力に精度・信頼度・信頼区間を表示しない
- 入力は `data/stores/<store_id>/` の YAML に人が書く。値ごとにステータス（OBSERVED / PUBLIC_VERIFIED / PUBLIC_REPORTED / ASSUMPTION / UNRESOLVED）・出典 ID・取得日を持たせる
- 出典台帳（sources.yaml）には URL・取得日・抜き出した事実だけを書き、ページ本文は保存しない
- 未確定の値は `value: null` と候補（candidates）で持ち、計算時に候補ごとに展開する。null を 0 として扱わない

## 捨てた案

- **食べログ・求人サイトのスクレイピング**: 利用規約の確認と許諾が無く、403 で取得もできない
- **ホットペッパー API で店舗情報を自動取得**: 利用ガイドの禁止事項と事業形態の適合を確認していない。将来の取り込みは別 issue で利用条件の台帳から始める
- **未確定値を代表値で埋めて 1 本の数字を出す**: spec 1.3・T17 が禁じる「暗黙の補完」になる

## 変えてよい前提 / 壊すと危ない前提

- **変えてよい**: YAML のキー名・ファイル分割、ステータスの表示名
- **壊すと危ない**: 「全入力にステータスと出典がある」「UNRESOLVED は候補に展開し 0 にしない」「精度を名乗らない」。これを崩すとレポートの数字が実績らしく見えてしまう
