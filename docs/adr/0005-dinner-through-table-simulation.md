# ADR 0005: 夜の客数も卓シミュレーションに通し、入れなかった分を失った需要として出す

## 背景

夜の客数は、需要（曜日ベース × 季節係数 × 特定日の効果）をそのまま入店客数にしていた。卓の数や団体予約で埋まる卓を見ていないので、2 階の卓構成の候補を変えても夜の売上がほとんど変わらず、候補を比べる意味が薄かった。

## 決定

- 夜も昼と同じ卓シミュレーション（`engine/tables`）に通す。団体予約は卓を占有するブロックとして先に置く
- 卓が足りずに入れなかった客を、理由（満卓・待ちの上限など）ごとの失った需要として出す
- 同じ条件の 1 日の結果は使い回す（`simulate_dinner_day` のキャッシュ）。感度分析で費用だけを振る行が速くなる

## 捨てた案

- 需要に「卓の稼働率の上限」を掛けて客数を出す案: 団体予約で卓がまとまって埋まる時間帯を表せない
- 乱数を用途ごとに分ける案（#30 の STEP B）: 分けても差のばらつきが変わらなかったので取り消した

## 守らせ方

- `tests/test_dinner_day.py`（入店 ＋ 失った需要 ＝ 希望人数、需要 0 で入店 0 など）

## 変えてよい前提 / 壊すと危ない前提

- 変えてよい: 失った需要の理由の分け方、キャッシュの持ち方
- 壊すと危ない: 夜の結果のキャッシュはテストのあいだも残る。内部の関数を monkeypatch で数えるテストを足すときは、最初に `clear_dinner_day_cache()` を呼ぶ
